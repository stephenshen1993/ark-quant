# 方舟计划全站设计升级规格

> 状态：已实施并通过验收（2026-08-06）
> 职责：定义账户、今日计划、更新日志三页的统一产品体验、数据 interface、响应式行为和验收基准。
> 真源范围：本轮 Web 体验升级的页面结构、交互状态、工程 seam 与视觉回归要求。
> 不负责：修改投资规则、策略参数、计算逻辑、账户事实口径或自动执行交易。
> 最后核对：2026-08-06

## 1. 来源与结论

本规格来自：

- `CONTEXT.md` 的“Web 产品体验词汇”；
- `/private/tmp/ark-quant-site-design-upgrade-prototype-handoff-2026-08-06.md`；
- `/private/tmp/ark-quant-site-design-upgrade-spec-handoff-2026-08-06.md`；
- 三方向可丢弃原型和独立交叉 review。

选定“执行平衡型”作为生产基线。页面围绕“事实 → 判断 → 执行”组织，使用克制的编辑感表达结论，使用精密的数据排版表达账户事实、偏离和动作；不采用内容站式过度留白，也不采用通用管理后台式高密度状态墙。

## 2. 产品目标

升级后的工作台必须让用户在首屏快速回答：

1. 当前事实是否足以形成计划；若不足，具体缺什么、去哪里更新。
2. 今天是否需要行动；若需要，按什么顺序手工执行。
3. 哪些资金当日可用，哪些只能次交易日或更晚确认。
4. 系统判断使用了什么事实与计算依据，但这些依据不抢占行动阅读。

更新日志继续承担连续阅读，不被改造成卡片后台。

## 3. 范围

### 3.1 本轮包含

- 统一“方舟计划｜个人投资系统”身份、导航、布局、颜色、字体、间距和状态语言。
- 默认入口改为“今日计划”，并支持账户、今日计划、更新日志三页直接链接、刷新和浏览器返回。
- 今日计划的五类用户状态：待补充事实、正在生成、今日无需操作、今日需要操作、计划已失效或失败。
- 账户页的事实就绪度首屏、A/B/C 组合层级和按异常出现的维护入口。
- 更新日志的连续阅读排版和既有五字段契约。
- 新增计划事实就绪度与最新生成生命周期的只读 interface。
- 三视口真实浏览器视觉回归和无障碍交互验收。

### 3.2 本轮不包含

- 修改投资规则、目标比例、阈值、交易日判断、选股或转债算法。
- 自动下单、自动调拨、成交回写或把建议标记成已成交。
- 新建独立仪表盘、绩效趋势、收益归因或行情模块。
- 更新日志搜索、筛选和工程审计字段。
- 深色模式、密度切换、首页/导航个性化或装饰动效。
- 为原型夹具增加数据库字段或硬编码账户金额、日期、证券和订单。

## 4. 当前工程事实

- 生产 UI 位于 `app/static/index.html`，使用 Alpine 状态和现有 FastAPI 路由；本轮不引入新的前端框架或构建链。
- 账户事实由 `app/account_read_model.py` 统一暴露 `accounts`、`portfolio_nodes`、`portfolios` 等 read-model。
- 当前计划由 `app/plan_service.py` 返回 `account_read_model`、`fund_transfer`、`execution_sequence`、`cb`、`stock` 等结构化结果。
- 完整计划校验包含 `stock`、`cb`、`changqian`、`cash`、`overseas` 五个账户，输入窗口由服务端业务日与策略运行信息决定。
- `execution_sequence` 的阶段顺序为 `sell → transfer → buy`；资金动作另有 `same_day`、`next_trading_day`、`deferred` 和 `cash_effect`。
- 生成生命周期持久化 `running`、`complete`、`failed`、`stale`，但当前只能按已知 `plan_id` 读取。
- 更新日志由 `app/static/changelog.json` 提供，公开字段只有 `date`、`time`、`type`、`title`、`body`。

## 5. module 与 interface 设计

### 5.1 账户 read-model 保持事实纯度

`app/account_read_model.py` 的 interface 继续只描述账户、策略承载与 A/B/C 组合层级。它不计算计划事实是否就绪，不读取市场温度，不复制计划输入窗口。

页面只使用 read-model 的公开字段，不使用 `legacy_adapter` 组织新界面，不把 legacy `strategy` 当作账户概念。

### 5.2 计划事实就绪度 module

在 `app/plan_service.py` 增加：

```python
build_plan_readiness() -> dict
```

这是账户页、计划页和测试共同使用的 interface。它隐藏以下实现：

- 当前计划基准日解析；
- 计划输入窗口结束日解析；
- 五个必备账户集合；
- `validate_account_inputs(..., include_overseas=True)`；
- 错误到逐账户状态的归一化。

HTTP adapter：

```http
GET /api/plan/readiness
```

正常业务状态始终返回 `200`，缺事实不是 HTTP 错误：

```json
{
  "plan_date": "YYYY-MM-DD",
  "input_window": {
    "start": "YYYY-MM-DD",
    "end": "YYYY-MM-DD"
  },
  "status": "ready | needs_facts",
  "accounts": [
    {
      "account_id": "stock",
      "account_name": "广发账户",
      "portfolio_id": "A",
      "snapshot_date": "YYYY-MM-DD | null",
      "status": "ready | missing | outside_window",
      "message": "string | null"
    }
  ],
  "errors": []
}
```

约束：

- `accounts` 按账户 read-model 的稳定顺序覆盖五个必备账户。
- `errors` 保留现有结构化校验错误，不让前端解析中文消息决定状态。
- 前端不得自行比较日期或维护必备账户常量。
- 账户页不得为了读取就绪度而调用整份 `/api/plan`。

### 5.3 最新生成生命周期 module

在 datasource 的本地 SQLite adapter 增加按计划日期读取最新生成记录的查询，在 `app/plan_lifecycle.py` 增加：

```python
get_latest_plan_status(plan_date: str | None = None) -> dict | None
```

未传 `plan_date` 时由 module 使用当前计划基准日。HTTP adapter：

```http
GET /api/plan/generated
```

响应：

```json
{
  "generation": {
    "plan_id": "string",
    "plan_date": "YYYY-MM-DD",
    "status": "running | complete | failed | stale",
    "error": "object | null",
    "created_at": "ISO-8601"
  }
}
```

无当前生成记录时返回 `200` 和 `{"generation": null}`。这个 interface 只暴露生命周期元数据，不返回或重新定义旧计划动作；当前建议仍来自当前计划 interface。

### 5.4 HTTP adapter 错误原则

- 业务上的 `needs_facts`、无生成记录、无动作都使用成功响应和明确状态。
- 无法建立计划基准日、数据库失败等真正系统错误保留结构化错误响应。
- 路由 adapter 不复制就绪度或生命周期判断，只调用 module interface。

## 6. 共享视觉系统

### 6.1 颜色

生产 token 以选定原型为基线：

| Token | 值 | 用途 |
| --- | --- | --- |
| `--paper` | `#f3f5f6` | 页面工作区底色 |
| `--surface` | `#ffffff` | 导航和主内容表面 |
| `--surface-soft` | `#edf1f2` | hover、次级状态 |
| `--ink` | `#17212b` | 主文字 |
| `--muted` | `#65717c` | 次要说明 |
| `--soft` | `#8e99a3` | 辅助元信息 |
| `--line` | `#d8dfe3` | 常规分割线 |
| `--line-strong` | `#bac5cb` | 结构边界 |
| `--accent` | `#0d716f` | 当前导航、链接和系统强调 |
| `--accent-soft` | `#dcecea` | 当前导航背景 |
| success | `#28724f / #e3f1e8` | 已就绪、保存成功 |
| warning | `#9a6108 / #f6ead5` | 待维护、当日动作提醒 |
| danger | `#a24343 / #f4e3e2` | 失败、失效、阻断 |
| info | `#315e86 / #e1eaf2` | 生成中、中性进度 |

不得使用渐变、玻璃拟态、黑金色系或常驻投影。颜色不是唯一状态载体，状态必须同时有文本或图形标识。

### 6.2 字体与数字

- 正文：`PingFang SC, Microsoft YaHei, Noto Sans CJK SC, sans-serif`。
- 展示标题：`Avenir Next, PingFang SC, sans-serif`。
- 金额、日期、代码和对齐数据：`DIN Alternate, SFMono-Regular, Menlo, Consolas, monospace`。
- 桌面页标题 `38px/1.15`，窄屏 `30px/1.15`。
- 正文默认 `14px`，说明文字不低于 `11px`；金额使用等宽或等宽数字特性。

### 6.3 几何基线

- `wide 1512 × 749`：左侧导航宽 `220px`；workspace 外框最大宽 `1140px`，左右内边距 `46px`，实际内容宽 `1048px`；内容起点约 `x=342px`。
- `desktop 1440 × 1000`：同样使用 `220px` 导航和 `1140px` workspace；内容起点约 `x=306px`。
- 桌面 workspace 顶部内边距 `54px`，底部保留完整滚动空间。
- 更新日志阅读列最大宽 `880px`，在 workspace 内容区内居中；它不复用工作台卡片宽度。
- 模块圆角 `6px`，使用边线建立层级，不以阴影分层。
- `narrow 390 × 900`：共享顶栏高 `64px`，workspace 左右内边距 `18px`，可用内容宽 `354px`，顶部内边距 `30px`。

这些值替代旧布局的精确坐标基准。实现若因真实字体换行需要微调，必须在同一票据中更新本规格、视觉闸门文档和脚本常量，不能只放宽断言。

## 7. 共享外壳与导航

- 用户可见主名称“方舟计划”，身份说明“个人投资系统”；不显示 `ark-quant` 品牌文案。
- 桌面使用固定宽度左侧导航，顺序为“今日计划、账户、更新日志”。
- 窄屏使用 `64px` 顶栏，保留同一顺序；不显示图标以避免拥挤。
- 默认 URL 为今日计划。三项导航必须是带真实 `href` 的链接，而不是只依赖点击事件的按钮。
- 当前页使用 `aria-current="page"`；刷新、浏览器前进/后退后当前状态与 URL 一致。
- 导航、按钮、输入、`summary` 等可交互元素使用至少 `2px` 的可见 `:focus-visible` 轮廓，不能用 `outline: none` 消除焦点。
- 桌面左侧底部常驻说明：计划需人工复核并在外部券商执行，系统不代表已经下单或成交。

## 8. 今日计划页

### 8.1 固定阅读顺序

页面顺序为：

1. 页面身份、说明和计划事实日期。
2. 今日结论。
3. 今日行动摘要；只在“今日需要操作”出现，必须紧接结论。
4. 计划事实就绪度。
5. 事实 → 判断 → 执行的解释脊柱。
6. 当前与目标配置偏离、资金可用性边界。
7. 账户间资金安排、订单明细和就近计算依据。

计算依据可以用 `<details>` 或等价渐进展开控件，默认不抢占首屏；展开控件的名称必须描述内容，例如“查看这笔调拨的计算依据”。

### 8.2 五类用户状态与优先级

| 优先级 | 状态 | 触发 | 首屏结论与动作 |
| --- | --- | --- | --- |
| 1 | 正在生成 | 本地 `POST /api/plan/generate` 请求未结束，或最新生命周期为 `running` | “正在生成完整计划”；使用 `aria-busy=true` 和不确定进度，不声称正在某个后端阶段 |
| 2 | 待补充事实 | readiness 为 `needs_facts` | 点名缺失或窗口外账户，显示输入窗口；链接到账户页对应维护位置 |
| 3 | 计划已失效或失败 | 最新生命周期为 `stale` 或 `failed` | 显示服务端 reason/stage/message；旧动作不作为当前建议展示；提供重新生成或先修复事实的动作 |
| 4 | 今日需要操作 | 当前计划可用且归一化行动数大于 0 | 显示动作总数和可复述的执行顺序 |
| 5 | 今日无需操作 | 当前计划可用且归一化行动数为 0 | 把“无需操作”作为完整结论，显示计划日期、事实窗口和判断依据 |

首次加载占位是短暂加载反馈，不是第六种用户状态。未知系统错误归入“计划已失效或失败”的错误表达，但保留结构化错误码供排查。

### 8.3 行动摘要归一化

页面使用结构化字段，不解析中文步骤文案：

- 卖出与买入使用 `execution_sequence[*].phase` 和对应 `orders`。
- 调拨使用 `fund_transfer.top_level.executed_actions`、`fund_transfer.top_level.outflows`、`fund_transfer.a_internal.actions`。
- `available_on=same_day` 的入金或调拨放在卖出后、买入前。
- `available_on=next_trading_day|deferred` 作为买入后的后续确认，不计入今日可买预算。
- `cash_effect`、`immediate` 和服务端金额用于标签和资金边界；前端不重算预算。
- 零股、零张和零金额动作不进入摘要；筛选依据使用结构化数值，不解析展示文本。

行动摘要每项至少显示：序号、人工动作、账户或证券、金额/数量、时序标签。证券订单仍显示成交结果以券商为准；不得出现“已执行”“已成交”等完成语义。

### 8.4 配置偏离与图表门槛

- 仅当 `fund_transfer.top_level.current`、`weights`、`targets` 可用时，显示 A/B/C 当前与目标的紧凑水平对比条。
- 每条必须同时显示精确当前金额、当前权重、目标权重或目标金额；图形不能替代数字。
- 不显示饼图、圆环图、收益曲线或用账户金额快照模拟绩效。
- 若数据不足，直接省略图形并显示结构化文字，不制造空图。

### 8.5 生成与错误反馈

- 常规主动作仍只有“生成完整计划”。
- 请求进行中禁用重复提交并显示明确 busy 文案；因为后端为同步工作流，前端使用不确定进度，不伪造实时阶段。
- 成功后使用返回的完整计划刷新所有区块，并重新读取最新生命周期。
- 失败显示 `error.stage`、`code`、`message`；局部策略失败不覆盖已知账户事实和资金边界。
- 账户事实改变导致 `stale` 后，不展示旧计划动作；页面明确要求重新生成。

## 9. 账户页

### 9.1 首屏顺序

1. 页面身份与说明。
2. 账户事实就绪度结论和计划输入窗口。
3. 异常账户维护入口；全部就绪时不突出维护按钮。
4. 全体系总资产。
5. A/B/C 资产结构与账户事实。

异常首屏必须点名账户，例如“华泰账户、海外长钱账户需要更新”，不能只显示数量。按钮“查看并更新这些账户”滚动到事实区，并把异常账户维护入口置于可见状态。

### 9.2 资产层级

- 顶层顺序使用 read-model 的 `portfolios`：A 自主管理组合、B 海外长钱组合、C 国内长钱组合。
- 每个组合显示 `current_amount` 和说明；子层使用 `portfolio_nodes` 与 `accounts` 关联。
- 账户显示名称、角色、金额、事实日期和就绪状态；账户是托管与执行位置，组合是资产层级。
- 金额为事实快照，不添加涨跌、收益或趋势含义。

### 9.3 维护交互

- 正常账户默认只提供次级“维护”入口；异常账户直接显示“更新事实”。
- 复用现有账户快照、持仓和 context 保存路由，不改变保存语义。
- 编辑区在对应账户附近渐进展开；桌面可以双列，窄屏必须单列，不使用横向滚动表单。
- 保存成功后重新加载 `/api/account/summary` 和 `/api/plan/readiness`，显示功能性成功反馈；若保存使已有计划失效，计划页通过生命周期 interface 展示 `stale`。
- 保存错误靠近对应表单显示，同时保留可重试输入，不只使用 toast。

## 10. 更新日志页

- 继续读取 `app/static/changelog.json`，按日期、时间倒序分组。
- 页面可见字段严格为日期、时间、类型、标题、正文；不展示 Issue、PR、提交、文件名、验收记录等工程元数据。
- 桌面阅读列最大宽 `880px`，日期组之间使用明显节奏；条目使用分割线而不是卡片。
- 每个日期使用一个 `h2`，每条日志使用 `article` 和 `h3`；全页只有一个 `h1`。
- 窄屏把元信息放到标题上方，正文保持自然换行；不压缩为横向两列。
- 数据加载失败显示页面内错误和重试入口，不把空数组误写成“暂无更新”。

## 11. 响应式与动效

### 11.1 桌面

- `>760px` 使用左侧导航和居中 workspace。
- 订单、偏离和账户事实允许结构化多列，但任何列都必须能在 `1440px` 完整阅读。
- 计算依据与高级维护默认折叠，不让页面变成无限展开的控制台。

### 11.2 窄屏

- `<=760px` 切换为顶栏和单列内容。
- 行动项由“序号 + 内容 + 时序”重排为两行或三行，时序不挤在最右侧。
- 订单表转换为语义完整的纵向条目，不依赖横向滚动查看证券、方向、数量和参考金额。
- A/B/C 与账户金额保留，次要角色说明可换行但不能隐藏异常和事实日期。
- 页面、控件和文本在 `390px` 下满足 `scrollWidth == clientWidth`。

### 11.3 动效

- 只允许生成中、展开/收起、保存成功和错误提示等功能性反馈。
- 非即时过渡在 `prefers-reduced-motion: reduce` 下关闭或缩短为近即时。
- 不使用入场、滚动、视差和数字滚动动画。

## 12. 无障碍与语义

- 页面使用 `nav`、`main`、`section`、`article`、标题层级和原生表单语义。
- 今日结论为页面主状态，可通过 `aria-live="polite"` 宣告生成结束、保存成功和错误；避免重复宣告整页。
- 生成区使用 `aria-busy`；错误文本与输入通过 `aria-describedby` 关联。
- 仅图形状态必须有文字；紧凑对比条提供可访问的数值文本。
- 所有点击目标在窄屏至少 `36px` 高，主要表单与导航目标优先达到 `42px`。

## 15. 验收标准

- 用户在首屏能识别当前计划状态、阻塞和下一步。
- 在不展开计算依据时，用户能按正确顺序复述今日动作，并区分当日资金与次日回流。
- “今日无需操作”有明确计划日期和判断依据，不表现为空白或禁用。
- 账户页能点名所有异常账户并直达维护位置；正常状态以资产结构为主。
- A/B/C 组合层级和账户角色来自 read-model，没有 legacy 概念回流。
- 更新日志保持连续阅读和五字段契约，同时与全站产品身份一致。
- `390px` 下关键信息优先、无横向裁切、键盘焦点可见。
- readiness 和生命周期判断均由服务端 module interface 提供，前端不解析中文消息或复制日期规则。
- 三视口视觉闸门、相关单元/集成测试、console/page error 检查全部通过。
- 生产页面不含原型控制器、夹具数据、自动成交暗示、绩效趋势、深色模式或装饰动效。
