# 方舟计划全站设计升级：UI/UX 对抗审查修复补充规格

> 状态：已实施并通过验收；独立 UI/UX 对抗复审结论为 `READY`
> 父规格：`2026-08-06-方舟计划全站设计升级.md`
> 职责：为已实施的全站设计升级补齐账户事实可信度、计划生成门禁与窄屏关键任务的可验收修复。
> 不负责：变更投资规则、账户事实口径、策略算法，或自动执行交易。
> 最后核对：2026-08-06

## Problem Statement

当前页面在正常数据下保持了“事实 → 判断 → 执行”的信息架构，但真实失败态和窄屏维护任务仍会产生危险的错误暗示：账户汇总读取失败会看起来像有效的零资产；切换账户事实日后，旧日期的行可被静默保存到新日期；计划尚不具备生成条件时仍可提交重复生成；390px 下账户维护和订单核验依赖横向滚动。

这会破坏个人投资系统最重要的可信度边界：用户无法可靠地区分“没有资产/无需操作”与“系统未能读取事实”，也可能误将错误日期、旧计划或不可执行状态视作可操作结论。

## Solution

在不推翻已选“执行平衡型”方向的前提下，补足以下闭环：

1. 账户事实请求的失败、真实空账户和已加载事实必须是三种不同的可见状态；失败时不显示或推断任何事实结论，并提供页面内重试。
2. 账户事实日是表单数据身份的一部分。日期变更后必须重新取得该日期数据；完成前阻止保存；加载失败或未保存编辑必须明确处理，绝不把旧行写进新日期。
3. 完整计划只在服务端就绪度允许、且没有同计划日 `running` 生成时才可生成。前端按状态引导用户修复事实、重试读取或等待，服务端保留并发重复提交的最终防线。
4. 390px 的账户维护和订单核验改为可完整阅读、可键盘操作的单列/纵向条目；保存和重试有清晰进行中、成功和错误反馈。
5. “今日行动摘要”只在当前有效计划确有动作时出现；“今日无需操作”保留为完整、带日期和依据的结论。

## User Stories

1. 作为个人投资系统使用者，我希望账户汇总读取失败时看到明确的失败状态和重试入口，以免把系统故障当成零资产。
2. 作为使用者，我希望真实空账户与读取失败的页面表达不同，以便判断是否需要录入事实还是重新请求。
3. 作为使用者，我希望请求失败时“事实已就绪”、总资产和资产结构不再宣称有效，以免基于未知事实作决定。
4. 作为使用者，我希望账户汇总、持仓或报价任一关键请求失败都能在相应语境中说明问题，以便知道不能依赖当前显示。
5. 作为使用者，我希望重试能重新读取所需账户事实和就绪度，以便从短暂服务故障恢复，而不必切换页面或刷新浏览器。
6. 作为使用者，我希望更改账户事实日后立即知道新日期正在加载，以免误以为屏幕上的旧行属于新日期。
7. 作为使用者，我希望日期对应数据加载失败时保留明确错误和重试入口，以免在不完整事实下保存。
8. 作为使用者，我希望有未保存编辑时日期切换受到明确门禁，以免意外丢弃编辑或混淆数据身份。
9. 作为使用者，我希望在新日期数据尚未确认前无法保存，以免把旧日期的持仓、现金或账户 context 写入新日期。
10. 作为使用者，我希望保存只在当前加载完成且未处于保存中时可提交，以免重复提交或产生歧义。
11. 作为使用者，我希望保存成功后得到可感知的成功反馈，并看到账户汇总与计划事实就绪度刷新，以便确认影响已生效。
12. 作为使用者，我希望保存失败保留已输入内容并在表单附近说明原因，以便修正后重试。
13. 作为使用者，我希望计划缺少事实时“生成完整计划”不能提交，并能直达需要维护的账户。
14. 作为使用者，我希望从计划页前往账户维护时，目标账户已经可见、对应维护区展开并获得键盘焦点，以便立即补充事实。
15. 作为使用者，我希望就绪度读取失败时不能生成计划，但可以就地重试读取，以免把未知状态当成已就绪。
16. 作为使用者，我希望已有生成正在运行时不能再次创建完整计划，以免重复计算或产生互相冲突的生命周期记录。
17. 作为使用者，我希望服务端也拒绝同计划日的并发重复生成，以便即使绕过界面或发生竞态也保持生命周期可信。
18. 作为使用者，我希望 `stale` 或 `failed` 计划仍可重新生成，以便修复条件后恢复工作流。
19. 作为手机使用者，我希望在 390px 宽度完整维护账户事实，不必横向滚动寻找代码、数量、现金、删除或保存控件。
20. 作为键盘和辅助技术使用者，我希望账户现金、代码、数量、删除和保存控件都有可访问名称和清晰焦点，以便独立完成维护。
21. 作为手机使用者，我希望主要维护和保存点击目标达到可可靠触达的尺寸，以免误触。
22. 作为手机使用者，我希望计划订单以含证券、方向、数量和参考金额的纵向条目呈现，以便不横向滚动完成核验。
23. 作为使用者，我希望无动作时不看到“今日行动摘要”，以免把无须操作误解为遗漏或伪造的执行任务。
24. 作为使用者，我希望“今日无需操作”仍明确呈现计划日期和判断依据，以便将无动作理解为有效结论。
25. 作为维护者，我希望真实浏览器闸门覆盖上述失败态、日期身份、生成门禁和窄屏展开任务，以避免正常态截图掩盖回归。

## Implementation Decisions

- 保持账户 read-model、计划事实就绪度 interface 和计划生命周期 interface 的既有边界；前端不自行推断账户日期、必备账户或计划可执行性。
- 账户加载状态按数据类型建模，至少区分未加载、加载中、成功事实、真实空数据与失败。失败不得降级为可用的零值或“已就绪”。
- 账户事实日切换以日期为加载键。只有该键对应的 summary、positions、quotes 均已确定，且页面没有待处理加载或错误时，才允许保存同一键的编辑值。
- 未保存编辑的日期切换采用明确、可恢复的交互门禁；实现不得静默丢弃编辑，也不得把编辑迁移到另一个日期。
- 账户保存拥有单一进行中锁；开始保存后禁用重复提交，结束时用表单附近的成功或错误反馈收口，并在成功后重新读取账户事实与计划就绪度。
- 计划页的生成资格来自 readiness 与最新 generation 生命周期。`needs_facts` 导向账户维护，readiness 错误只允许重试读取，`running` 禁止重复提交，`stale`/`failed` 保持重新生成入口。
- 计划生成用例在生成入口增加同计划日 `running` 互斥检查；冲突必须返回结构化、用户可恢复的结果，不能仅依赖前端禁用按钮。
- 计划到账户的深链接携带目标账户标识；到账户页后滚动、展开和焦点移动必须发生在相应数据加载完成之后。
- 窄屏账户维护使用原生、带名称的表单控件和单列编辑布局；删除使用文字或 `aria-label`，不可去除可见焦点；互动目标遵循父规格的最小触达尺寸。
- 窄屏订单以语义完整的纵向条目表达；桌面仍可保持可扫描的表格布局。
- “今日行动摘要”的渲染条件收紧为“当前有效计划且归一化动作数大于零”；无动作结论不以空的摘要容器占位。
- 状态和错误消息保持区分“账户事实”“系统判断”“人工执行”三层，不把计划生成或建议表述为成交。

## Testing Decisions

- 优先在现有账户 API、计划 API、页面行为测试和真实浏览器视觉闸门这些最高可观察 seam 断言用户可见行为，而非断言内部变量或 DOM 实现细节。
- 账户场景必须覆盖 summary、positions、quotes 的非成功 HTTP 响应和网络失败，以及真实空账户；断言三者在结论、资产数值、错误与重试行为上可区分。
- 日期身份测试必须拦截请求，验证变更日期会读取对应日期数据；在加载、错误或 dirty 门禁期间保存请求不会发生；成功保存的日期和载入行属于同一事实日。
- 保存测试必须覆盖重复点击、进行中禁用、成功后的双重刷新，以及失败后输入保留与表单内错误。
- 计划测试必须覆盖 `needs_facts`、readiness 错误、`running`、`stale`、`failed` 和可生成状态，且包含服务端并发/重复生成最终防线。
- 深链接测试必须验证目标账户的滚动、展开和焦点，而不仅是页面切换或滚到顶部。
- 390px 真实浏览器测试必须检查展开后的账户维护和订单条目，断言无横向裁切、焦点可见、标签完整及最小点击目标；不能只截首屏。
- 行动摘要测试必须以结构化动作构造有动作/无动作场景，确认无动作时摘要不可见而结论、日期和依据仍可见。
- 每张实施票采用先失败测试、最小修复、聚焦回归；完成后执行 Standards 与 Spec 双轴代码审查。全量收口重跑单元测试、Ruff、差异检查、三视口视觉闸门及独立 UI/UX 对抗审查。

## Out of Scope

- 投资规则、策略参数、再平衡公式、交易日判断、账户事实业务口径和数据库领域模型改造。
- 自动下单、自动调拨、成交回写、绩效趋势、深色模式、个性化导航或装饰性动效。
- 推翻账户首屏“事实就绪度优先，资产结构承载内容，维护动作按异常出现”的信息架构。
- 更改更新日志的数据字段契约或将其改造成工作台卡片流。
