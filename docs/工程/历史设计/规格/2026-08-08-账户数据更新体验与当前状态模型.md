# 方舟计划账户数据更新体验与当前状态模型规格

> 状态：已实施并验收（2026-08-08）
> 职责：定义逐账户当前状态、单账户更新交互、计划生命周期联动和兼容迁移。
> 真源：`CONTEXT.md`、`2026-08-08-账户数据更新交互原型结论.md`
> 不负责：修改账户层级、资产配置规则、策略选券、订单 sizing、自动下单或成交回写。
> 最后核对：2026-08-08

## 1. 结论

账户页面向用户只表达“查看和更新某个账户的当前数据”。账户历史版本仍可作为系统内部复核材料存在，但不得再以全局账户事实日、全账户快照、沿用历史或批量录入的形式成为用户任务。

正式界面采用原型 A「账户工作台」：账户总览负责定位账户与判断更新需要，单账户编辑视图负责预填当前数据、编辑变化、核对影响和明确保存。

## 2. 用户任务与状态

### 2.1 账户总览

账户总览必须：

- 继续先表达逐账户计划就绪度，再展示既有组合与账户层级。
- 使用“账户”和“账户数据”，不再把“账户事实”作为页面主命名。
- 每个账户独立展示数据截至时间、是否需要更新、记录状态和更新入口。
- 缺失或过期时可在顶部汇总异常账户，但不得出现统一事实日或全账户批量保存。
- 账户状态至少区分：尚未录入、当前可用、需要更新、已确认空仓、估值暂不可用、读取失败。
- 尚未录入不得显示为 `¥0.00` 或“暂无持仓”；只有明确保存的零金额或空仓才是真实零值。

### 2.2 单账户编辑

点击账户更新入口后进入该账户自己的编辑视图：

- 页面始终显示账户身份、当前数据截至时间、当前状态和计划影响。
- 打开即预填该账户当前数据，不增加“查看态 → 编辑态”切换。
- 证券账户同时展示可用现金、冻结现金和全部当前持仓。
- 金额账户只展示并预填该账户金额。
- 用户离开、返回总览、切换导航或关闭页面时，如有未保存修改必须提醒。
- 保存成功后留在当前账户，刷新数据时间、派生金额与完成提示。

## 3. 原始数据与派生数据

### 3.1 证券账户原始数据

用户只维护：

- 证券代码。
- 持仓数量。
- 可用现金。
- 冻结现金。

约束：

- 证券代码标准化为六位代码，并在一个账户内唯一。
- 添加已有代码时定位原持仓，不创建重复行。
- 数量必须是有限非负数；数量归零等同于单只证券清仓。
- 保存后不保留零数量持仓。
- 冻结现金和可用现金均必须是有限非负数。
- 证券名称不是用户输入；名称识别失败不改变代码与数量的可保存性。

### 3.2 派生数据

证券名称、最新价格、单只市值和证券账户总资产均为系统派生结果：

- 总资产 = 可用现金 + 冻结现金 + 所有持仓的最新市值。
- 页面不得要求用户填写或修正总资产。
- 行情可用时显示派生结果及其行情时间。
- 行情不可用时派生结果返回“暂不可计算”，不得用零值代替。
- 行情失败不阻塞原始数据保存，但依赖估值的计划生成必须进入阻塞状态。

金额账户的金额本身是用户维护的原始数据，不属于证券估值。

## 4. 当前账户状态 module

建立深的“当前账户状态 module”，seam 位于账户 HTTP adapter 与 SQLite/行情/计划生命周期 implementation 之间。页面、计划就绪度和测试均通过同一 interface 使用当前账户状态，不再各自拼接账户金额、持仓快照与日期。

### 4.1 Interface

module 对调用方提供四项能力：

1. `list_current_accounts()`：返回账户总览需要的五个账户状态。
2. `get_current_account(account_id)`：返回一个账户完整的当前原始数据、派生数据、版本与数据时间。
3. `update_current_account(account_id, expected_version, raw_data)`：以服务器当前时间提交普通更新。
4. `confirm_current_account(account_id, expected_version)`：确认原始数据未变化，只刷新该账户数据时间。

旧数据补录是次级 interface，只接受明确的历史数据时间；补录结果只进入追溯记录，不替换或创建时间更新的当前状态，也不物化为计划会读取的 operational snapshot。

### 4.2 当前状态返回模型

每个账户返回：

- `account_id`、账户名称与账户类型。
- `record_state`：`missing` 或 `recorded`。
- `as_of`：该账户数据日期；缺失时为 `null`。
- `updated_at`：该账户版本写入时间；缺失时为 `null`。
- `version`：用于并发保护的不可猜测版本标识；缺失时为 `null`。
- `raw_data`：金额账户为 `amount`；证券账户为现金与持仓。
- `holding_state`：证券账户使用 `missing`、`recorded` 或 `confirmed_empty`；尚未录入不返回空仓。
- `valuation`：`available` 或 `unavailable`，并携带可用的价格、市值、总资产和行情时间。
- `readiness`：账户记录与估值本身是否可用；相对当前计划输入窗口的判断统一由计划 readiness interface 返回，账户页将两者合并展示。
- 计划 readiness 读取失败或缺少某账户结果时，合并状态为 `unknown`；页面显示“待确认”和重试入口，不计入已就绪账户。

接口不得用空数组或零金额同时表达“缺失”和“已确认零值”。

### 4.3 当前版本选择

- 每个账户独立选择当前版本。
- 当前版本按 `as_of DESC`、同日再按版本顺序选择，不能只按最后写入顺序选择。
- 证券账户的现金与持仓必须来自同一次账户版本，不得拼接不同时间或不同保存批次的数据。
- 后录入的旧日期版本只进入追溯记录，不改变当前版本。

### 4.4 更新原子性

- 证券账户现金与全部持仓必须在同一个事务中全有或全无地保存。
- 任一校验或持久化步骤失败时，旧当前状态保持不变。
- HTTP 失败后页面保留用户草稿，不重新加载为空白或旧编辑值。
- 金额账户各自独立保存，不与其他账户组成跨账户事务。

### 4.5 并发保护

- 普通更新和确认均必须提交打开编辑视图时获得的 `expected_version`。
- 当前版本已变化时返回 `409 Conflict` 和最新版本摘要，不能静默覆盖。
- 页面保留草稿，提示用户加载最新账户数据后重新核对。

## 5. 保存意图与计划生命周期

### 5.1 普通更新

- 任一原始数值发生变化后，主操作为“保存账户数据”。
- 保存区持续列出本次变化；点击主操作即提交，不再弹普通确认框。
- 实际变化保存成功后，清除基于旧输入的派生订单并把当前计划标记为失效。

### 5.2 数据仍准确

- 原始数据没有变化时，主操作为“确认数据仍准确”。
- 确认刷新该账户的数据时间，并保持证券账户现金与持仓为同一个确认版本。
- 确认不得清除订单或使当前计划失效。

### 5.3 高风险零值

- 金额账户保存为零金额，或证券账户保存为全部持仓清空时，必须二次确认。
- 普通金额修改、数量修改、单只证券增删不增加二次确认。
- 二次确认必须明确说明保存后形成真实零金额或已确认空仓，不是“尚未录入”。

## 6. HTTP adapter

已实施的用户交互端点：

- `GET /api/accounts`：账户总览当前状态列表。
- `GET /api/accounts/{account_id}`：单账户当前状态。
- `PUT /api/accounts/{account_id}`：提交普通当前状态更新。
- `POST /api/accounts/{account_id}/confirm`：确认数据仍准确。

普通证券账户更新请求只包含：

- `expected_version`。
- `available_cash`。
- `frozen_cash`。
- `positions: [{code, quantity}]`。

金额账户更新请求只包含 `expected_version` 与 `amount`。正常更新请求不包含用户选择的日期、证券名称或总资产。

旧的按日期 summary、snapshot 与 state 端点在迁移期只承担兼容，不再由账户主界面调用；兼容资格检查与 legacy 写入处于同一个串行化事务。某账户形成非 backfill 的新模型当前版本后，旧写端点对该账户返回 `409`；即使新旧写入并发发生，也只能有一方完成，避免形成两套当前状态真相。

## 7. 账户编辑视觉结构

### 7.1 桌面

- 使用原型 A 的账户工作台结构。
- 主列依次为现金与当前持仓；右侧为 sticky 的变化摘要与主操作。
- 右侧摘要不把变化项数量做成页面主视觉，不使用“步骤数”或工作量叙事。
- 当前持仓以中高密度表格呈现，代码与名称同组，数量可编辑，价格与市值只读。

### 7.2 `390px` 窄屏

- 导航保持现有移动形态。
- 现金、持仓、变化摘要与主操作改为单列。
- 持仓表转换成纵向记录，不允许依赖横向滚动完成编辑。
- 主操作宽度与触控区域足够，原型切换器不得进入生产。

## 8. 错误、空态与完成态

- 读取失败：显示请求失败和重试，不展示缓存零值或空仓结论。
- 尚未录入：明确说明此账户没有当前数据，并提供首次录入入口。
- 已确认空仓：显示有效数据时间、现金和“已确认空仓”，可继续添加证券。
- 行情失败：保留编辑能力，派生列显示不可计算，计划生成说明阻塞原因。
- 保存失败：显示账户级错误，保留草稿，旧当前状态不变。
- 更新冲突：保存不可继续，保留草稿并提供加载最新数据入口。
- 保存成功：留在当前账户，显示刷新后的数据时间；实际变化同时显示计划已失效。

## 9. 兼容与迁移

- 迁移前先为现有五个账户建立当前版本读取基线，不删除任何历史记录。
- 修正账户金额当前态选择规则：由最大写入 `id` 改为数据日期优先、同日版本优先。
- 证券持仓当前态沿用 `position_date DESC, id DESC`，但必须与同一次账户版本保持一致。
- 证券账户的新写入不再接受用户提供的总资产；旧 `total` 字段只能作为兼容数据，不能继续成为用户输入真源。
- 若估值在持久层允许缺失，所有 read-model 和计划校验必须显式处理 `null`，不得回退为零。
- 当前生产账户页的全局日期选择、roll-forward 草稿、跨账户保存和批量保存入口全部退出主流程。

## 10. 测试与验收

### 10.1 Module 测试

- 五个账户分别读取自己的当前版本与数据时间。
- 后写入的旧日期版本不替换当前版本。
- 缺失、零金额与已确认空仓三态不混淆。
- 证券账户更新现金或持仓任一失败时整次回滚。
- 同一账户重复证券代码被拒绝或归并为原持仓，不形成重复记录。
- `expected_version` 过期返回冲突且不覆盖新状态。
- 实际变化使计划失效；确认无变化不使计划失效。
- 行情失败仍可保存原始数据，估值返回 unavailable。

### 10.2 HTTP 与页面测试

- 正常请求不含日期、名称或总资产。
- `409`、校验错误和读取失败均有结构化响应。
- 页面打开直接显示预填持仓与现金。
- 无修改与有修改时主操作文案正确切换。
- 普通保存一次提交；整账户清空出现二次确认。
- 保存成功留在当前账户，失败或冲突保留草稿。
- `390px` 无横向溢出，所有字段和主操作可通过键盘与触控访问。

### 10.3 回归命令

- `.venv/bin/python -m unittest discover -s tests -v`
- `.venv/bin/ruff check .`
- UI smoke 覆盖账户总览、证券账户编辑、金额账户编辑，以及 wide、desktop、narrow 三类视口。

## 11. 明确不做

- 不新增面向用户的账户历史浏览器。
- 不实现跨账户统一保存或统一确认。
- 不把内部账户快照提升为页面概念。
- 不增加自动同步券商、自动下单、成交回写或绩效账本。
- 不直接复制 throwaway 原型代码到生产。
