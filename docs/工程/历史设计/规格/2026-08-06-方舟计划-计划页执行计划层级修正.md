# 方舟计划：计划页执行计划层级修正规格

> 状态：已实施并通过验收
> 职责：修正“今日需要操作”状态下的执行信息层级，使资金调拨动作归属于资金调拨计划、证券交易明细归属于具体账户交易计划。
> 真源范围：完整计划的用户可见执行 read model、计划页行动区、响应式明细和对应验收门槛。
> 不负责：修改投资规则、资金来源追踪、自动执行、成交回写或账户与更新日志页面重构。
> 最后核对：2026-08-06

## Problem Statement

当前计划页把所有证券买卖和资金调拨展平成一条跨账户行动列表，并用“今日动作 N 项”“N 个步骤”概括结果。这种表达把证券交易明细从所属账户交易计划中剥离，也把不同账户的计划误写成一个可连续执行的全局流程。

实际领域关系是：用户先审阅资金调拨计划，确认各账户的资金前提与可用时点，再审阅具体账户交易计划；每笔证券买卖只在所属账户计划中有意义。资金账户用于解耦现金流，进入资金账户的资金一视同仁，因此调入和调出都是独立的单腿动作，不能被界面配对为来源账户到目标账户的端到端资金路径。

本次修正必须让用户回答三个问题：今天有哪些执行计划、哪些账户需要先获得资金、每个账户计划在资金与买卖完成后是否闭合。全局笔数、步骤数和工作量不是需要表达的产品事实。

## Solution

把“今日需要操作”改造成纵向执行卷宗：首屏仅给出判断、事实日期与执行日期；正文先展示资金调拨计划，再展示按资金前提排序的账户交易计划。

完整计划响应增加一个面向用户的执行 read model，服务端统一完成账户身份解析、资金动作归组、账户资金前提判断、卖出与买入分项汇总、资金闭合校验以及稳定排序。页面消费该结构，不再从混合执行序列推导全局步骤，也不再从 legacy 策略标识猜测账户身份。

资金调拨计划只在至少存在一项调拨时成立并默认展开，按资金可用时点分组。每项调拨独立表达来源、目标、金额、原因和可用时点，不建立资金账户两侧动作之间的配对关系。

账户交易计划以具体账户为主身份，以所属组合和策略为副信息。计划默认收起逐笔明细，摘要直接显示交易日、资金前提、卖出/买入分项和完整资金算式。展开后只展示实际存在的卖出或买入阶段；桌面使用交易表，窄屏改排为无横向滚动的两行记录。

## User Stories

1. 作为计划审阅者，我希望首屏先看到“今日需要操作”的结论，而不是一个交易笔数，以便把它理解为决策结果而非工作量统计。
2. 作为计划审阅者，我希望看到计划使用的事实日期和计划执行日期，以便确认计划是否适用于当前交易日。
3. 作为资金安排者，我希望在账户交易计划之前看到资金调拨计划，以便先确认哪些账户具备执行所需资金。
4. 作为资金安排者，我希望无调拨动作时完全不出现资金调拨计划，以免空模块暗示存在资金安排。
5. 作为资金安排者，我希望有调拨动作时资金调拨计划默认展开，以便无需额外交互即可先完成资金审阅。
6. 作为资金安排者，我希望调拨按当日可用、下一交易日可用和更晚可用分组，以便明确当日执行边界。
7. 作为资金安排者，我希望每项调拨显示单向来源、目标、金额、原因和可用时点，以便独立执行和复核。
8. 作为资金安排者，我不希望系统把调入资金账户和从资金账户调出配成一条资金路径，以免产生不存在的来源归属。
9. 作为计划审阅者，我希望账户交易计划以真实账户名称作为标题，以便知道应在哪个券商或账户中执行。
10. 作为计划审阅者，我希望组合和策略只作为账户标题的副信息，以便理解计划来源而不混淆执行位置。
11. 作为计划审阅者，我希望账户计划按资金已具备、需要当日调入、等待未来资金可用的顺序出现，以便先处理当前可执行计划。
12. 作为计划审阅者，我希望同一资金前提内保持固定账户顺序，以便每日快速形成稳定的阅读习惯。
13. 作为执行者，我希望账户计划摘要同时显示卖出笔数、预计卖出金额、买入笔数和预计买入金额，以便理解计划结构而非只有净额。
14. 作为执行者，我希望账户计划显示“起始可用资金 + 调入 - 调出 + 预计卖出 - 预计买入 = 计划后预计资金余额”，以便复核资金是否闭合。
15. 作为执行者，我希望金额算式的每个分项都来自同一计划 read model，以免页面自行计算造成口径漂移。
16. 作为执行者，我希望计划后预计资金余额不足时，该账户明确表现为被阻断，而不是普通可执行计划。
17. 作为执行者，我希望账户计划默认收起证券交易明细，以便先完成账户级审阅，再按需查看逐笔订单。
18. 作为执行者，我希望展开账户计划后先看到卖出阶段、再看到买入阶段，以便遵循先释放资金后使用资金的账户内依赖。
19. 作为执行者，我希望没有证券交易明细的阶段完全不出现，以免把空阶段误认作待执行工作。
20. 作为执行者，我希望没有证券交易明细的账户不生成账户交易计划，以免出现没有执行意义的账户卡片。
21. 作为执行者，我希望每笔明细保留清仓卖出、减仓、新买入和加仓语义，以便准确理解策略意图。
22. 作为执行者，我希望桌面交易表显示动作、证券代码与名称、数量、参考价和估算金额，以便完成逐笔复核。
23. 作为移动端用户，我希望在 390px 宽度下以两行记录查看同样的关键字段，以便无需横向滚动。
24. 作为计划审阅者，我希望运行中、失效或失败计划不展示为当前可执行卷宗，以免依据旧动作执行。
25. 作为计划审阅者，我希望未来才可用的资金只影响账户资金前提，不被表示为当日买入预算。
26. 作为计划审阅者，我希望计划页不出现全局行动序号、步骤数或逐笔交易总数，以免再次把账户计划展平。
27. 作为维护者，我希望执行信息的聚合与排序由一个纯 read-model 构造边界完成，以便对领域层级做集中测试。
28. 作为维护者，我希望既有完整计划字段在迁移期间保持兼容，以便本次修正不改变策略生成和资金计算算法。

## Implementation Decisions

### 1. 深化完整计划响应，而不是在页面重新聚合

完整计划增加 `execution_read_model`。它是计划页唯一的用户可见执行结构，包含可选的 `funding_plan` 与有序的 `account_trading_plans`。既有混合执行序列可以为兼容用途保留，但新计划页不得用它构造行动区。

read model 由纯构造函数生成：输入为已生成的完整计划和统一账户 read model，输出不读取数据库、不依赖请求上下文，也不产生副作用。它隐藏 legacy 策略标识到真实账户身份的映射、分项汇总和排序细节。

### 2. 资金调拨计划结构

`funding_plan` 在无有效调拨动作时为 `null`；有动作时包含按可用时点排序的 `groups`。每个 group 提供机器可判定的 availability、显示日期和动作数组。

每个动作至少包含来源账户标识与名称、目标账户标识与名称、金额、原因、机器可判定的可用时点和显示日期。动作保持现有单腿事实；聚合器不得匹配入金和出金，不得增加资金来源批次或端到端路径标识。

分组稳定顺序为当日可用、下一交易日可用、更晚可用；同组内保持计划生成结果的稳定顺序。零金额动作不进入 read model。

### 3. 账户交易计划结构

每个账户计划包含账户标识、账户名称、组合名称、策略名称、交易日、资金前提、资金算式与实际存在的交易阶段。账户名称来自统一账户 read model；legacy adapter 仅可作为服务端内部解析手段，不成为新的页面契约。

资金前提使用机器状态 `ready`、`needs_same_day_transfer`、`waits_for_funds` 和 `blocked`，并提供资金可用日期。前端只映射状态文案和样式，不根据金额或日期重新判定状态。

账户计划排序先按 `ready`、`needs_same_day_transfer`、`waits_for_funds`、`blocked`，再使用统一账户 read model 的稳定顺序；不得按证券笔数、金额或页面临时排序。

没有非零买卖订单的账户不产生账户交易计划。`HOLD`、零数量和零估算金额记录不进入交易阶段。

### 4. 资金闭合结构

每个账户计划的 `cash` 同时提供：起始可用资金、调入、调出、预计卖出、预计买入、计划后预计资金余额。所有金额使用现有计划计算结果与订单估算真源，在服务端按同一舍入规则归一化。

闭合恒等式为：`起始可用资金 + 调入 - 调出 + 预计卖出 - 预计买入 = 计划后预计资金余额`。计划后预计资金余额是计划估算，不是实际余额或成交结果。

若预计余额低于允许边界，账户计划状态必须为 `blocked`，响应提供结构化阻断原因；页面不得仅以说明文字继续呈现为普通可执行计划。本次不修改资金规划算法，若生成结果发生不闭合，只负责忠实暴露和阻断。

### 5. 账户内阶段与证券交易明细

`phases` 只包含实际存在的 `sell` 和 `buy` 阶段，固定先卖后买。订单保留结构化动作 `SELL`、`TRIM`、`BUY`、`ADD`，以及证券代码、名称、数量、单位、参考价和估算金额。

阶段和订单只属于当前账户计划，不提供跨账户全局序号。展示文案不得称其为“全局动作”或“步骤”。

### 6. 页面信息架构

“今日需要操作”首屏保留判断、事实日期和执行日期，移除所有全局数量表达。行动区按以下固定顺序渲染：资金调拨计划、账户交易计划。

资金调拨计划有动作时默认展开。账户交易计划默认仅显示账户身份、交易日、资金前提、卖出/买入分项和资金算式，逐笔明细由原生可访问的展开控件打开。

桌面明细采用五字段表格；窄屏将每笔订单改排为两行语义完整记录。响应式变化只调整布局，不删除动作、证券身份、数量、参考价或估算金额。

### 7. 生命周期门禁与兼容

执行 read model 只在当前完整计划可执行时供页面展示。生成中、失效和失败状态继续服从既有计划生命周期优先级，旧计划动作不得透过新组件显示。

本次保留现有完整计划原始字段，避免影响生成、持久化和其他调用方。新页面迁移完成后是否清理旧展示字段另行评估，不纳入本次范围。

## Testing Decisions

### 最高测试 seam

以“完整计划输入 → `execution_read_model` 输出”的纯构造函数作为最高价值 seam。测试通过公开构造边界断言领域层级，不复制内部辅助函数、账户映射或页面算法。HTTP 测试只确认完整计划响应正确暴露该 read model；页面测试确认只消费这一结构。

### Read-model 契约测试

- 有调拨时生成资金调拨计划，无调拨时为 `null`。
- 调拨动作保持单腿来源与目标，不出现配对路径字段；零金额动作被过滤。
- 调拨按当日、下一交易日、更晚可用分组并保持稳定顺序。
- 真实账户名称、组合和策略来自统一账户 read model，legacy 标识不泄露为页面身份。
- 账户计划按资金前提和固定账户顺序排列。
- 无有效订单的账户、空阶段、`HOLD`、零数量和零金额订单不进入输出。
- 卖出与买入分项金额、笔数和完整资金恒等式准确，舍入口径稳定。
- 当日调入、未来可用和资金不足分别映射为对应结构化资金前提；资金不足必须为 `blocked`。
- 订单动作保留清仓卖出、减仓、新买入和加仓语义，阶段固定先卖后买。

### HTTP 与生命周期测试

- 完整计划成功响应包含稳定的 `execution_read_model`，既有原始字段保持兼容。
- 生成中、失效和失败状态不能作为当前可执行 read model 被页面展示。
- 无动作计划仍走“今日无需操作”状态，不生成空资金计划或空账户计划。
- 真正系统错误保留既有结构化错误契约。

### 页面行为测试

- “今日需要操作”不包含全局行动数、步骤数、逐笔总数或全局序号。
- 有调拨时资金调拨计划先出现并默认展开；无调拨时不出现。
- 账户计划按约定顺序出现、默认收起，展开后只出现实际存在的卖出和买入阶段。
- 资金前提、卖出/买入分项和完整资金算式均可见；阻断账户不使用普通可执行样式。
- 桌面五字段齐全；390px 两行记录字段齐全且 `scrollWidth == clientWidth`。
- 键盘可展开资金依据和账户明细，焦点可见，展开控件提供正确的可访问名称与状态。

### 真实浏览器视觉闸门

在既有 smoke 入口增加四类场景：默认动作场景、等待未来资金场景、展开账户明细、无调拨/无动作边界。继续覆盖 1512px、1440px 和 390px，断言无横向溢出、无全局步骤文案、资金计划先于账户计划、移动明细关键字段完整。

## Out of Scope

- 自动下单、自动调拨、券商连接、完成勾选、成交回写和实际余额回写。
- 记录或展示资金账户余额中资金的来源账户、入账批次或端到端去向。
- 修改资金调拨算法、投资比例、选股或转债策略、订单数量和估价规则。
- 新增账户、组合或策略，或重命名既有账户事实。
- 重构账户页、更新日志页或全站视觉系统。
- 新增绩效、收益归因、行情、工作量或任务进度模块。
- 将原型方向切换器、夹具数据或原型静态结构带入生产页面。
- 为本次展示修正引入新的前端框架、构建链或数据库 schema。
- 清理所有 legacy 完整计划字段；兼容字段退役需要独立任务和调用方证明。
