# 当前实现状态

> 状态：当前工程事实
> 职责：汇总 ark-quant 已实现能力、已知限制和与投资体系的主要差距。
> 真源范围：2026-07-22 的代码、测试和当前运行路径。
> 不负责：把现有实现升级为正式规则，或决定尚未盘定的战术。
> 最后核对：2026-07-22

## 1. 总体判断

当前系统已经形成“当前账户事实—策略榜单—目标金额—资金调拨计划—交易计划”的基本链路，方向上接近当前 MVP。MVP 只要求快速、可靠地生成资金调拨计划和交易计划，不要求成为完整投资体系、投资账本、绩效平台或无人值守交易系统。主要短板应按这一边界判断，而不能把尚未建设执行跟踪和绩效账本本身视为 MVP 缺陷。

## 4. 主要差距

### 4.1 已确认战术的当前落地

#### 4.1.1 2026-07-21 已落实的资金调拨最小闭环

资金调拨已新增独立纯规划器：按 A/B/C 温度映射计算账户间目标；月度检查只使用已确认新增本金与真实现金，季度/临时检查按严格外带宽触发半带宽修复。B 的实际申购额度、核验时间和来源作为检查事实保存；额度缺失即不可申购，受限 B 流入会同步缩减来源流出，不把缺口转给其他目标。

`/api/plan/transfer` 只依赖账户快照、温度和调拨检查事实，必须有股票、转债、国内长钱、海外长钱和现金快照，但不读取任何账户内榜单。计划页保持这项后端分层，由唯一常规主按钮依次保存本次条件、补齐缺失榜单、重新计算两类订单并汇总 `/api/plan`；某一策略局部失败不会遮蔽另一策略结果。资金调拨、转债计划和股票计划三张结果卡始终显示，无需调拨会明确写出，不再因隐藏第一部分出现编号断层。

页面只按本次目的展示相关输入。B 申购事实显式区分尚未核验、已核验不可申购和已核验可申购；后两者必须有核验时间与来源，可申购还必须有正额度。榜单手工生成和市场温度外部刷新进入折叠的高级操作。所有动作仍只生成计划，不自动下单、不追踪成交，也不把预计卖出或赎回款当作即时现金。

2026-07-22 已补齐成交后防重复执行边界：账户和持仓按声明的事实日期进入计划输入窗口，录入时间不再掩盖旧口径日期；任一账户事实或本次计划条件更新后，当前派生订单自动失效，但同日榜单保留并可重新计算。系统仍不记录“已经执行”状态，真实调仓完成后由人保存最新账户、现金和持仓事实，下一次计划从这些事实重新开始。

本轮 A 内部新旧目标切换已经按正式新目标生成的完整计划人工执行，因此不为这次一次性迁移增加阶段字段、旧公式兼容分支或执行状态机。执行前生成的旧计划现只具备历史参考意义，在成交后事实尚未更新前不得再次执行。

尚未落实的内容主要包括：B 多承载通道汇总、首次顶层完整季度迁移的专门验收，以及依据后续真实使用记录校准形成期阈值。它们继续以体系规则为准，不由当前实现倒推规则。

体系级战术已经确认了 A/B/C 顶层架构、`70/15/15` 至 `65/20/15` 的温度映射、A 组合内部三锚点与分段线性映射、反映多数股票体感的全市场温度输入及简化换源治理、C 固定 `15%`、B 动态 `15%-20%`、月度软偏离修复、季度“相对 `10%` 且绝对 `3` 个百分点封顶”的硬偏离线、越线后的半带宽修复、受限去向的部分可执行修复、首次完整季度迁移、基于 `A_exec` 的两层预算衔接、QDII 三状态与恢复规则、B 替代载体硬门槛、A 内部千元级净调拨门槛、围绕现金池的星型调拨、顶层与 A 内部共享即时现金上限、现金不足时的缺口分配、执行失败后按事实重算、可转债 `130 元`实际买入硬上限、交易单位可执行性检查、分层检查频率和人在回路的 MVP 边界。账户内交易定额已经切换为股票与转债共享的等权字典序 MILP，统一覆盖 Top 20、全局离散比较、费用、余现、风险上限与失败关闭；剩余差距主要在计划后权重和求解证据展示，详见 [交易计划定额验收差距](交易计划定额验收差距.md)。正式规则见 [仓位与再平衡规则](../体系/仓位与再平衡规则.md) 和 [交易执行规则](../体系/交易执行规则.md)。

当前实现已经覆盖 A/B/C 顶层目标、A 内部动态目标、月度与季度检查分层、半带宽和受限去向处理、`A_exec`、现金池星型调拨、共享账户内离散等权订单以及旧计划不接续等主链路。仍需补齐计划页面的逐标的权重、余现归因和求解证据，并继续收口 B 多承载通道、极端输入和外部数据失败场景；不能因为主链路已经可用，就把形成期参数升级成未经验证的长期最优参数。

小市值账户内订单由共享等权字典序 MILP 生成，命令行与计划 API 使用同一套 Top 20、100 股整手、单股 `10%` 上限、动态普通订单门槛、必要卖出冻结和正式费用规则。容量冲突、缺报价、求解未证明最优或现金约束失败会停止生成订单，不以第 21 名或局部启发式替代；该能力仍只生成计划，不跟踪真实成交。

### 4.2 计划生成仍需对齐正式战术

当前代码中的仓位公式、调拨阈值、调拨结构和订单约束仍需随正式战术共识逐项校正。MVP 是否完成，应优先检查同一组有效输入能否快速、稳定、可解释地生成正确的资金调拨计划和交易计划。

### 4.3 策略证据不足

两条策略都有当前可运行版本，但关键参数和完整历史表现仍缺少与真实约束一致的系统回测、滚动区间检查和实盘归因。可转债专题差距见 [可转债策略实现差距](实现状态/可转债策略实现差距.md)。

### 4.4 工程与平台限制

- 当前 Web、API 和 SQLite 是本地实现，不是长期底座承诺。
- 策略 Web 运行锁是进程内锁，不解决多进程并发。
- 外部数据源仍存在可用性和字段稳定性风险。
- 订单只生成计划，系统不知道真实成交、部分成交、费用和滑点；这符合当前 MVP 边界，不要求人工写回 ark-quant。
- 账户标识和部分 API 路径仍保留历史上的 `strategy` 命名，需要靠文档和模型接口避免概念混淆。

### 4.5 非 MVP 扩展

全体系外部入金、生活分红、个人生产力支出、累计盈利台阶、沪深 300 全收益基准、MWR/TWR、计划执行状态和真实成交归因均不属于当前 MVP。长期投资账本继续使用已有三年多记录的有知有行投资账本；只有 MVP 好用并出现明确新增价值后，才评估是否同步、迁移或补充其中某些能力。

## 5. 后续顺序

1. 继续从投资体系出发盘清仓位与再平衡战术。
2. 将确认后的战术落实为清晰的资金调拨计划和交易计划口径，再评估 MVP 代码改造。
3. 验证同一输入能否快速、稳定、可解释地生成计划，并改善人工执行前的准备效率。
4. 用回测和外部实盘记录验证账户内策略参数。
5. MVP 稳定好用后，再决定是否增加执行跟踪、绩效或账本等能力，以及哪些继续交给成熟平台。

在第一步完成前，不把现有公式、比例、频率或页面交互当作约束。
