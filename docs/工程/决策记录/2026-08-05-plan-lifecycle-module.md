# 计划生命周期 module 决策记录

> 状态：当前工程决策记录
> 职责：说明计划生命周期 module 的边界、interface 建模方式和第一阶段治理节奏。
> 真源范围：计划生成状态、阶段日志、错误记录和订单批次登记的工程组织方式。
> 不负责：定义资金调拨算法、订单 sizing 算法、投资规则或 SQLite 表结构细节。
> 日期：2026-08-05；最后核对：2026-08-05

## 1. 决策

计划生命周期需要形成独立 module。它只管理计划从生成到完成、失败或失效的生命周期事实，不吞掉资金调拨算法和账户内策略的订单 sizing 算法。

该 module 的主 interface 采用状态机，阶段日志作为审计细节。

主状态包括：

- `draft`：尚未生成。
- `running`：生成中。
- `complete`：已完成。
- `failed`：失败。
- `stale`：已失效，需要重新生成。

阶段日志用于解释状态变化，例如准备账户事实、生成资金调拨计划、生成转债订单、生成股票订单、写入订单批次、完成或失败。

订单批次由计划生命周期 module 负责登记、保存和读取；订单内容仍由资金调拨 module 或策略 sizing module 产出。

## 2. 背景

当前计划相关逻辑分散在 `app/plan_service.py`、`app/routers/plans.py` 和 `datasource/db.py` 之间：

- 计划生成状态、错误记录和订单批次持久化混在计划编排和数据门面里。
- HTTP 路由中仍存在订单 sizing 适配逻辑。
- 页面和测试需要理解多个内部字段，才能判断计划是否已经生成、失败或需要重新生成。

这会降低 locality：计划生命周期规则变化时，调用方容易被迫一起修改。

## 3. module 边界

计划生命周期 module 负责：

- 开始生成计划。
- 推进计划阶段。
- 标记完成、失败或失效。
- 记录失败原因。
- 登记订单批次。
- 读取已有订单批次和计划状态。
- 向 API 和页面提供稳定的计划生命周期 interface。

计划生命周期 module 不负责：

- 计算资金调拨金额。
- 决定股票或转债买卖数量。
- 获取外部行情。
- 定义投资体系目标比例、阈值或执行规则。
- 在第一阶段修改数据库表结构。

## 4. 第一阶段节奏

第一阶段先做入口和 interface 收敛：

1. 从现有计划编排中识别生命周期读写点。
2. 建立计划生命周期 module。
3. 让计划编排和 HTTP adapter 通过该 module 使用生命周期能力。
4. 保留现有 `generated_plans` 和 `plan_order_batches` 表。
5. 用现有 API 与计划测试保护行为不变。

数据库 schema 是否调整，留到第二阶段按真实压力再判断。

## 5. 与既有决策的关系

[数据源仓储 seam 决策记录](2026-08-04-datasource-store-seams.md) 已明确：`generated_plans` 和 `plan_order_batches` 暂不按表机械拆分，应等计划生命周期设计成熟后再处理。

本决策确认了该触发条件，但第一阶段仍不改表结构。这样可以先得到更深的 module interface，再决定是否需要新的 store。

## 6. 验证约束

计划生命周期治理至少满足：

- `ruff check .` 通过。
- `python -m unittest discover -s tests` 通过。
- 现有计划生成、失败记录、订单批次展示和盘中保护行为不退化。
- API 和页面不直接依赖生命周期 implementation 细节。
