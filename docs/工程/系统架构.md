# 系统架构

> 状态：当前工程事实
> 职责：描述 ark-quant 现有模块、入口和主要数据流。
> 真源范围：2026-08-05 代码与测试所体现的当前实现。
> 不负责：证明投资规则正确，或承诺未来继续采用当前技术栈。
> 最后核对：2026-08-05

## 1. 总体结构

```text
外部市场数据与人工账户事实
          ↓
datasource/ 数据访问与校验
          ↓
strategies/ 账户内策略运行 ←── app/strategy_runner.py
          ↓                         ↓
       SQLite ←── app/plan_generation.py ←── app/ API ──→ Web 看板
          ↑                         ↓
investment_model.py + rebalance.py → 目标金额与调拨步骤
```

这张图只表达当前工具结构。目标金额规则的正确性由 [仓位与再平衡规则](../体系/仓位与再平衡规则.md) 决定，不由 `rebalance.py` 决定。

## 2. 模块职责

| 模块 | 当前职责 |
| --- | --- |
| `app/` | FastAPI 应用、薄 API 路由、计划编排模块和静态 Web 看板 |
| `app/plan_generation.py` | 计划生成用例 module，负责计划上下文、资金调拨预览、当前计划预览、完整计划生成、按策略测算入口和已生成计划读取 |
| `app/strategy_runner.py` | 策略运行 adapter module，负责显式运行策略、为计划日确保榜单就绪、运行锁、持久化结果校验和策略运行错误分类 |
| `app/plan_service.py` | 计划服务兼容与过渡 helper，保留历史入口和共享计算 helper；新计划用例调用方应优先依赖 `app/plan_generation.py` |
| `app/plan_lifecycle.py` | 计划生命周期 module，负责计划状态、订单批次登记、失败记录和失效标记的稳定 interface |
| `app/order_sizing.py` | 订单 sizing 编排 module，负责把计划现金、榜单、持仓和报价转成账户内策略订单草案 |
| `app/account_read_model.py` | 账户事实 read-model interface，负责区分账户、账户内策略和 A/B/C 组合层级 |
| `datasource/` | SQLite 连接/迁移/兼容门面、市场行情、市场温度和交易日数据访问 |
| `datasource/account_store.py` | 账户上下文、账户价值快照、当前账户摘要和账户历史的持久化实现；`datasource.db` 保留兼容入口 |
| `datasource/position_store.py` | 持仓快照、持仓明细、as-of/日期窗口读取和旧式持仓兼容列表的持久化实现；`datasource.db` 保留兼容入口 |
| `datasource/strategy_store.py` | 策略运行、可转债/股票排名和衍生订单的持久化实现；`datasource.db` 保留兼容入口 |
| `strategies/cb_rotation/` | 多因子可转债候选、调仓与订单数量计算 |
| `strategies/stock_smallcap/` | 小市值股票候选、调仓与订单数量计算 |
| `investment_model.py` | 当前账户、策略、资产类别及承载关系的工程表达 |
| `rebalance.py` | 当前国内目标金额、偏离和资金调拨步骤计算 |
| `value_accounts.py` | 使用持仓和报价辅助估算股票、转债账户价值 |
| `config/` | 当前策略与数据获取参数，不是规则真源 |
| `portfolios/` | 当前本地持仓和旧式账户状态输入 |
| `data/` | SQLite、原始快照、处理中间数据和缓存 |
| `outputs/`、`logs/` | 每次运行的生成物和日志，不是正式文档 |

## 3. 运行入口

- `python3 run_app.py`：启动本地看板；`app.main` 初始化 SQLite 并挂载四组 API 路由。
- `scripts/ui_smoke.py`：唯一最高层 [Web 视觉回归闸门](视觉回归闸门.md)。它使用隔离 SQLite 和临时端口启动 app，再通过真实浏览器检查账户页、计划页、更新日志页在宽屏、桌面和窄屏视口下的可见行为、导航状态、计算样式、关键坐标、布局尺寸、横向溢出和 console/page error；失败截图、页面文本与结构化差异写入 `outputs/ui-smoke/`。
- `python3 -m strategies.cb_rotation.run`：运行可转债策略并持久化完整策略运行。
- `python3 -m strategies.stock_smallcap.run`：运行小市值股票策略并持久化完整策略运行。
- `python3 rebalance.py`：使用当前账户事实和温度计算目标与调拨报告。
- `python3 value_accounts.py`：按行情辅助估值账户。

## 4. 主要数据流

### 4.1 账户与持仓事实

人工在 Web 页面录入账户余额和持仓，API 分账户写入账户价值快照；股票和转债的账户状态保存会把账户价值与持仓快照放在同一事务中。读取时再聚合为当前账户视图。

账户事实与策略信号分开保存。账户是托管与执行位置，策略是决策逻辑，当前一一承载不构成架构约束。

### 4.2 策略运行

两条策略从外部数据源取得市场数据，过滤和排序后生成榜单。一次完整运行先创建 `strategy_runs` 记录，再在事务内写入对应排名并标记完成；这组策略运行、排名和订单 SQL 由 `datasource/strategy_store.py` 承接，`datasource.db` 继续提供兼容函数。Web 触发和计划生成自动补齐榜单都通过 `app/strategy_runner.py`，同一进程内同一策略只允许一个运行。计划生成不能通过排名 HTTP 路由触发策略运行。

榜单结合持仓、报价和可用现金后生成订单数量。订单是辅助执行草案，不是成交事实。

### 4.3 本期计划

计划生成用例 module 取得市场温度所对应的计划日，校验账户事实和策略输入的时间窗口，然后：

1. 聚合当前国内再平衡对象金额。
2. 调用当前仓位实现计算目标和偏离。
3. 生成账户间资金调拨步骤。
4. 汇总两条账户内策略的榜单或订单。
5. 返回执行顺序、警告和现金摘要。

关键输入不一致时返回错误，不应生成貌似完整的计划。计划 API 路由只把编排结果转换为 HTTP 响应，并把编排错误转换为 HTTP 错误。

完整计划生成从 Plan Generation 用例入口进入。该入口负责确保计划日所需策略榜单就绪、调用资金调拨和订单 sizing 编排、推进计划生命周期，并把失败归因到计划输入、策略榜单、资金调拨或订单测算等阶段。旧 `plan_service` 只保留兼容入口和可继续下沉的共享 helper。

## 5. 持久化边界

当前使用 `data/ark_quant.db` 的本地 SQLite。主要数据组包括：

- 策略运行、可转债/股票排名和订单。
- 分账户价值快照与账户上下文。
- 持仓快照及其明细。
- 原始数据快照。
- 市场温度和刷新状态。

旧式账户和持仓表仍为兼容迁移保留。表结构是当前工程细节，业务语义见 [投资记录与绩效口径](../体系/投资记录与绩效口径.md)。

## 6. 验证边界

`tests/` 覆盖数据库事务、账户/持仓 API、计划日期一致性、温度缓存与并发、两条策略的核心过滤和订单写入，并保留更新日志结构、排序、字段白名单和工程元数据隔离契约。`scripts/ui_smoke.py` 作为单独的 AIHOT 视觉回归闸门，不混入默认快速单元测试；它覆盖账户页、计划页、更新日志页在宽屏、桌面和窄屏视口下的可见行为、计算样式、关键坐标、布局尺寸、横向溢出和 console/page error。工程行为变化应更新或补充测试；视觉基准更新遵循 [Web 视觉回归闸门](视觉回归闸门.md)，规则变化必须先在相应规则文档达成共识。
