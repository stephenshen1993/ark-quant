# 系统定位与边界

> 状态：正式工程边界
> 职责：说明 ark-quant 在投资体系中的位置、应该做什么和不应该做什么。
> 真源范围：系统职责、非目标、规则与实现的优先关系。
> 不负责：定义投资战略、仓位公式、策略参数或日常操作步骤。
> 最后核对：2026-07-18

## 1. 一句话定位

`ark-quant` 当前 MVP 是个人投资体系的计划生成辅助工具：人提供生成本次计划所需的最新事实并决定何时触发，工具按已确认规则快速生成资金调拨计划和交易计划，随后由人自行审核和执行。投资体系属于人，工具可以修改、缩小或替换。

## 2. 真源关系

```text
投资体系与策略规则
        ↓ 约束
ark-quant 工程实现
        ↓ 生成
页面、API、榜单、订单和报告
```

工程实现只能落实已经确认的规则。代码、配置、数据库字段和页面文案即使已经存在，也不能证明规则正确或已经定型。

发生冲突时：

1. 保留体系与策略文档中的已确认共识。
2. 在 [当前实现状态](当前实现状态.md) 或专题差距文档中登记偏差。
3. 战术仍在盘点时暂停参数性改动，先完成讨论。
4. 共识明确后再修改实现并验证。

## 3. 当前职责

- 接收并校验生成本次计划所需的账户、持仓、市场温度和可用资金等当前事实；保存这些输入不等于承担长期投资账本职责。
- 运行账户内策略，将规则转成候选榜单与订单草案。
- 在人发起常态或临时检查后，按当前战术规则计算国内目标金额、资金调拨计划和交易计划。
- 检查关键输入是否齐全、日期是否一致、现金是否可用。
- 通过本地页面和导出材料降低重复计算、手工计算和漏项风险。
- 保留计划输入、生成时间和原始输出，使同一份计划能够解释和复核。

## 4. 明确非目标

- 不替代投资体系，不替用户决定尚未盘定的战略或战术。
- 不以实现便利为理由把账户、策略和资产类别混成同一层。
- 不预测短期行情，不把模型输出包装成确定性结论。
- 不自动决定何时需要调仓，不持续监控市场后自行触发计划。
- 不连接 QMT、券商或基金平台自动下单、申赎，不以系统结果覆盖真实成交和余额。
- MVP 不跟踪计划是否执行、部分成交、跨日执行、费用、滑点或人工如何落实，也不管理计划执行状态。
- MVP 不建设或迁移长期投资账本，不替代当前由有知有行投资账本承载的三年多手工记录、资金流和绩效历史。
- 不自研所有数据、回测、账户管理和展示能力；成熟外部工具可以替换任何工程层。
- 不把当前 Web 看板当作最终产品或长期必须保留的界面。

## 5. 可迁移性要求

真正需要长期保留的是规则、记录语义、输入和决策证据，而不是某个框架。系统演化应优先保证：

- 数据可导出并能追溯到时间与来源。
- 规则文档不依赖 Python、SQLite、FastAPI 或当前平台名称。
- 策略输出与账户事实分开保存。
- 新底座能够承接账户、策略和资产类别的独立关系。
- 替换工具后仍能复核同一次计划为什么产生。

## 6. 安全原则

系统默认本地运行。关键输入缺失、日期不一致、数据源失败或现金不可确认时，应停止生成可执行结果。

当前 MVP 安全边界为：

```text
人工触发
-> 系统按规则计算
-> 输出资金调拨计划和交易计划
-> ark-quant 本次职责结束
-> 人工复核并自行决定是否以及如何执行
```

计划输出后，是否执行、何时执行、如何执行以及如何记账均由人和外部平台承接，ark-quant 不执行真实交易，也不要求把执行结果写回为一套自建投资账本。下一次生成计划时，重新以当时券商、银行、基金平台等提供的最新账户和持仓事实为输入；旧计划不能覆盖新事实，也不需要在 ark-quant 内接续执行状态。

当前长期投资账本继续使用有知有行投资账本维护。该平台是当前好用且已积累历史记录的外部工具，不是投资体系战略真源；未来只有出现明确收益时才讨论迁移、同步或补充能力。

MVP 运行稳定并真正节省时间后，再独立评估执行跟踪、账本、绩效、自动触发或自动交易等扩展。任何扩展都不能因为技术上能够实现就默认进入范围；自动化交易尤其必须重新盘定权限、金额上限、异常停止、数据失效、人工撤回和审计规则。
