# 工程收口与底座评估备忘

> 日期：2026-07-13  
> 背景：方舟计划前一轮可靠性改造已经推进到一半，但投资体系文档化后，项目定位从“继续自研完整投资系统”调整为“保护投资体系，系统实现随行就市”。  
> 目标：避免继续扩大当前 ark-quant 的沉没成本，同时不丢掉已经有价值的工程成果。

## 1. 当前结论

方舟计划不应继续按“把本地 Web 打磨成完整最终产品”的路线推进。

更合理的定位是：

```text
投资体系：长期资产，需要沉淀、验证、迁移。
当前系统：临时实现，用来承载账户录入、策略榜单、调拨和交易计划。
外部底座：可替换对象，优先复用成熟的数据、回测、组合管理能力。
```

因此，前一轮系统改造需要收口，而不是继续一路做完。

## 2. 已经值得保留的方向

这些改动或设计即使未来换底座，也仍然有价值：

| 方向 | 保留理由 |
| --- | --- |
| 有知有行温度快照与缓存 | 温度是体系核心输入，必须可追溯，不能每次实时漂移 |
| 账户快照 | 账户金额和更新时间是事实记录，不能为了计划逻辑改写 |
| 持仓快照 | 股票/转债真实持仓是交易计划输入，必须区别缺失和空仓 |
| 策略榜单运行记录 | 榜单必须有数据日期、策略版本和完整性状态 |
| 日期一致性检查 | 账户、温度、持仓、榜单不能混用不同日期 |
| fail closed | 缺数据、口径不一致、数据源失败时停止生成计划 |
| 投资体系接口抽象 | 方便未来接 Ghostfolio、backtrader、vectorbt 或其他平台 |

这些属于“体系可迁移能力”，不是单纯 Web 功能。

## 3. 暂停扩展的方向

这些方向技术上正确，但现阶段先不继续扩大：

| 方向 | 暂停理由 |
| --- | --- |
| 完整交易计划版本化 | 会深度绑定当前 Web/API/SQLite 实现，迁移前投入偏重 |
| 前端复杂状态联动 | 主要服务当前界面，未来如果换底座可能重做 |
| 浏览器端请求数治理 | 是当前实现体验问题，不是体系核心资产 |
| 本地订单持久化闭环 | 有价值，但要等底座评估后决定放在哪一层 |
| 自研回测引擎 | 明确不做，优先接成熟框架 |

暂停不等于否定，只是避免在平台方向未定前继续加深绑定。

## 4. 前一轮可靠性改造状态

根据 2026-07-12 的执行记录：

| 任务 | 状态 | 处理建议 |
| --- | --- | --- |
| 温度新鲜度、缓存、校验 | 已完成并通过测试 | 可保留，属于核心输入可靠性 |
| 账户与持仓快照 | 已完成并通过测试 | 可保留，属于事实记录层 |
| 策略榜单完整性 | 基本完成，但质量审查仍有问题 | 只修最小问题后收口，避免继续扩展 |
| 交易计划不可变版本 | 未开始或未完成 | 暂停，等底座评估后再决定 |
| 前端精确日期状态 | 未完成 | 暂停，除非当前系统继续作为主操作台 |
| 交易日历与浏览器验收 | 未完成 | 暂停，后续按选定底座重新规划 |

策略榜单完整性当前遗留问题：

- 已完成的 strategy run 仍可能被二次写入排名。
- 旧库迁移后的 `strategy_runs.status` 缺少等价约束。
- 排名接口的运行锁是进程内锁，跨进程不可靠。

如果继续保留当前系统作为近期操作台，应优先只修这三个点，然后停止扩大改造。

## 5. 当前工作区处理原则

在没有明确继续开发当前系统前，不做大规模代码整理或重构。

建议：

1. 不回滚已有改动，避免丢掉已完成的可靠性工作。
2. 不继续实现 plan_versions、plan_orders 和前端状态大改。
3. 如果需要临时使用当前系统，只运行已覆盖测试的路径。
4. 把未完成设计保留在 `docs/工程记录/`，作为后续参考，不当成必须执行的路线。
5. 新增工程投入优先服务“可迁移接口”，而不是当前页面体验。

## 6. 下一阶段底座评估

底座评估不追求一次迁移，而是回答三个问题：

```text
1. 哪个平台最适合承载账户、资产、交易记录？
2. 哪个框架最适合承载策略信号回测？
3. ark-quant 最后应该缩小成哪一层？
```

候选方向：

| 层 | 优先评估 |
| --- | --- |
| 账户/组合管理 | Ghostfolio、自建轻量账户库、表格/数据库 |
| 数据获取 | AkShare、Tushare、本地 CSV/缓存 |
| 回测 | backtrader、vectorbt、果仁网 |
| 投资体系编排 | ark-quant 或独立规则服务 |

## 7. 底座评估验收尺子

评估时以 `docs/体系/个人投资体系规则书.md` 为准，重点检查：

- 是否能区分资产类别、策略、账户三类概念，并把国别表达为资产/策略属性。
- 是否能表达国内再平衡目标及其目标金额规则。
- 是否支持多账户和真实更新时间。
- 是否能保存账户、持仓、策略信号的历史快照。
- 是否能导入股票/转债策略榜单。
- 是否能表达账户间调拨计划。
- 是否能强制同一计划口径日。
- 是否能导出数据，避免平台锁死。
- 是否降低心智成本，而不是引入更复杂的维护负担。

无法满足日期绑定、调拨计划和可迁移导出的平台，只能作为展示层或辅助工具。

## 8. 推荐下一步

短期：

1. 保留投资体系文档和当前可靠性设计文档。
2. 暂停交易计划版本化和前端大改。
3. 用一到两天做 Ghostfolio / backtrader / vectorbt 的最小 spike。

中期：

1. 把 ark-quant 中的体系规则整理成平台无关接口。
2. 选择一个外部工具承载账户或回测，不再自研完整底座。
3. 当前系统只保留无法外包的投资体系编排能力。

最终目标：

```text
投资体系清晰、规则可迁移、数据可导出、回测可外包、操作可复盘。
```
